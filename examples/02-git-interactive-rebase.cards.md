# 知识卡片：用交互式 rebase 把凌乱的提交整理成一条干净的历史

## 卡片 1：交互式 rebase 用来在合并之前整理凌乱的提交
- **核心知识**：交互式 rebase 用来在合并之前整理一批凌乱的提交。
- **简明解释**：它允许你重写这批提交：合并、改写说明、调整顺序、删掉多余的那几个。整理的理由是：不整理的话，合并进主干之后，后来的人读历史会很痛苦。
- **例子或自测**：源文场景：一个功能分支上堆了七八个 "fix typo"、"wip" 之类的提交，需要在合并进主干之前重写。

---

## 卡片 2：只有非共享的分支才能改写历史
- **核心知识**：只有当这些提交还没有推到共享分支、或者即使推过也只有你一个人在用这个分支时，才能做交互式 rebase。
- **简明解释**：改写已经在别人本地拉了的历史，会给他们制造麻烦。判断标准很简单：除了你还有别人会基于这个分支工作吗？
- **例子或自测**：自测：源文用来判断一个分支能不能做交互式 rebase 的问题是什么？答：除了你还有别人会基于这个分支工作吗？

---

## 卡片 3：第一步，确认起点
- **核心知识**：开始 rebase 前先确认起点：数清当前分支相对主干多出的提交，并确认工作区是干净的。
- **简明解释**：`git log --oneline main..HEAD` 只列出当前分支有、main 没有的提交，数一下有几个，心里对要整理的范围就有个数。再用 `git status` 确认工作区；有未提交的改动时不要开始 rebase。
- **例子或自测**：命令：`git log --oneline main..HEAD` 用来数出要整理的提交，`git status` 用来确认没有未提交的改动。

---

## 卡片 4：第二步，进入交互模式
- **核心知识**：用 `git rebase -i` 加一个起点参数进入交互模式，编辑器里一行一个提交。
- **简明解释**：要把当前分支最近的 5 个提交一起处理，用 `git rebase -i HEAD~5`。想把从分叉点开始的全部提交都处理，先用 `git merge-base main HEAD` 找出分叉点，再把它作为参数传给 rebase。编辑器里每行由"动作 + 提交哈希 + 提交说明"组成，顺序是从旧到新。
- **例子或自测**：命令：`git rebase -i HEAD~5` 把当前分支最近的 5 个提交一起处理。

---

## 卡片 5：第三步，选择动作
- **核心知识**：常用的动作只有四个：`pick`、`reword`、`squash`、`fixup`。
- **简明解释**：`pick` 保留这个提交、不改动；`reword` 保留改动内容，但停下来让你重写提交说明；`squash` 把这个提交并入上一个提交，并把两条说明合并起来让你编辑；`fixup` 同样并入上一个提交，但直接丢弃这条提交说明。列表里最上面那一行不能用 squash 或 fixup，因为它上面没有可合并的目标。
- **例子或自测**：源文场景：整理 typo 类提交时，保留每个功能提交的 `pick`，把后面的修修补补改成 `fixup`。

---

## 卡片 6：第四步，解决冲突与中途退回
- **核心知识**：rebase 中途出现冲突时会停下来，处理完用 `git rebase --continue` 继续；发现整理方向错了，可以随时用 `git rebase --abort` 退回。
- **简明解释**：冲突时 rebase 会把冲突标记写进文件，处理完先 `git add <冲突文件>`，再 `git rebase --continue`。`git rebase --abort` 会把分支恢复到开始 rebase 之前的状态。
- **例子或自测**：命令：冲突处理后 `git add <冲突文件>`，然后 `git rebase --continue`；中途想退回就 `git rebase --abort`。

---

## 卡片 7：不要在 rebase 中途随意 `--skip`
- **核心知识**：不要在 rebase 中途随意 `--skip`，因为跳过一个提交意味着丢掉它的改动。
- **简明解释**：只有在你能确认那个提交的内容已经包含在别处时，跳过一个提交才是安全的。
- **例子或自测**：自测：在什么前提下才可以在 rebase 中途 `--skip` 一个提交？答：确认那个提交的内容已经包含在别处。

---

## 卡片 8：rebase 后推送用 `--force-with-lease`
- **核心知识**：rebase 之后如果需要推送，通常要加 `--force-with-lease`。
- **简明解释**：它比 `--force` 安全，因为如果远端有你不知道的新提交，它会直接失败，而不是覆盖别人的工作。
- **例子或自测**：自测：源文说 `--force-with-lease` 比 `--force` 安全在哪里？答：远端有你不知道的新提交时，它会直接失败而不是覆盖别人的工作。
