# 用交互式 rebase 把凌乱的提交整理成一条干净的历史

## 什么时候需要它

一个功能分支上如果堆了七八个 "fix typo"、"wip" 之类的提交，合并进主干之后，后来的人读历史会很痛苦。交互式 rebase 允许你在合并之前重写这批提交：合并、改写说明、调整顺序、删掉多余的那几个。

前提：这些提交还没有推到共享分支，或者即使推过，也只有你一个人在用这个分支。改写已经在别人本地拉了的历史，会给他们制造麻烦。

## 第一步：确认起点

先看当前分支和主干的关系：

```
git log --oneline main..HEAD
```

这条命令只列出当前分支有、main 没有的提交。数一下有几个，心里对要整理的范围有个数。同时确认工作区是干净的：

```
git status
```

有未提交的改动时不要开始 rebase。

## 第二步：进入交互模式

如果要把当前分支最近的 5 个提交一起处理：

```
git rebase -i HEAD~5
```

想把从分叉点开始的全部提交都处理，可以先用 `git merge-base main HEAD` 找出分叉点，再把它作为参数传给 rebase。

编辑器打开后，你会看到一行一个提交，每行由"动作 + 提交哈希 + 提交说明"组成，顺序是从旧到新。

## 第三步：选择动作

常用的动作只有四个：

- `pick`：保留这个提交，不改动。
- `reword`：保留改动内容，但停下来让你重写提交说明。
- `squash`：把这个提交并入上一个提交，并且把两条说明合并起来让你编辑。
- `fixup`：和 squash 一样并入上一个提交，但直接丢弃这条提交说明。

整理 typo 类提交时，通常的做法是保留每个功能提交的 `pick`，把后面的修修补补改成 `fixup`。列表里最上面那一行不能用 squash 或 fixup，因为它上面没有可合并的目标。

## 第四步：解决冲突

合并或改写提交的过程中如果出现冲突，rebase 会停下来，把冲突标记写进文件。处理完后：

```
git add <冲突文件>
git rebase --continue
```

中途发现整理方向错了，可以随时退回：

```
git rebase --abort
```

这条命令会把分支恢复到开始 rebase 之前的状态。

## 第五步：检查结果

rebase 结束后，重新看一遍历史：

```
git log --oneline main..HEAD
```

确认提交数量、顺序和说明都符合预期，并且工作区里的代码内容没有变化。可以用 `git diff <原始分支位置>` 来确认代码本身没有被意外改动。

## 常见坑

- 不要对共享分支做交互式 rebase。判断标准很简单：除了你还有别人会基于这个分支工作吗？
- 不要在 rebase 中途随意 `--skip`。跳过一个提交意味着丢掉它的改动，除非你确认那个提交的内容已经包含在别处。
- rebase 之后如果需要推送，通常要加 `--force-with-lease`。它比 `--force` 安全，因为如果远端有你不知道的新提交，它会直接失败而不是覆盖别人的工作。
- 编辑器里的提交顺序就是最终顺序。想调整先后，直接剪切粘贴整行即可，不必先改动作再调整。
